LongChainRAG

一个检索增强问答系统的完整实现：把文档灌进知识库，提问时先检索再回答， 并且每个结论都能点回到原文片段。面向电商商品知识库场景。 An end-to-end retrieval-augmented QA system: ingest documents, retrieve before answering, and let every claim link back to the passage it came from. Built for an e-commerce product knowledge base.

RAG 里最容易被低估的一步是检索Retrieval is the underrated half of RAG

大多数人第一次做 RAG 会把注意力放在提示词上，但实际决定回答质量的是「有没有把正确的段落捞出来」。 提示词写得再好，检索没召回目标段落，模型也只能编。所以这个项目在检索链路上做了三层—— Most people building their first RAG system focus on the prompt. What actually decides answer quality is whether the right passage got retrieved — a perfect prompt can't help if the passage never made it into context. So the retrieval path here has three layers.

一、混合检索：向量 + 关键词1. Hybrid retrieval: vectors plus keywords

纯向量检索对语义相近的表述很好，但对型号、编号、专有名词这类「必须逐字命中」的查询很糟—— 语义空间里「X200」和「X300」几乎挨在一起。补齐的做法是同时跑一路 BM25 关键词检索， 再把两路结果按 RRF（倒数排名融合）合并： Pure vector search handles paraphrase well but is bad at model numbers, IDs and proper nouns — the things that must match literally. In embedding space "X200" and "X300" sit almost on top of each other. So a BM25 keyword pass runs alongside it, and the two result sets are merged with Reciprocal Rank Fusion:

score(d) = Σ 1 / (k + rank_i(d))　（k = 60）

用排名而不是用分数融合，是因为两路检索的分数量纲根本不可比——余弦距离和 BM25 分数没有共同尺度， 归一化也只是掩盖问题。排名是无量纲的，融合起来才稳。 Fusing on rank rather than score is the point: cosine distance and BM25 scores have no common scale, and normalising them just hides that. Ranks are dimensionless, so fusing them is stable.

顺带一提，BM25 依赖在导入失败时不会让整个服务起不来——检索降级为纯向量，并留一条日志说明。 一个可选依赖不该让主流程挂掉。 The BM25 dependency also degrades gracefully: if the import fails the service still starts, retrieval falls back to vectors only, and a log line records it. An optional dependency shouldn't take down the main path.

二、重排序：保证来源多样2. Reranking: guaranteeing source diversity

检索回来的前几条经常来自同一份文档的相邻段落——它们内容重复，却把上下文位置全占了， 其他文档里真正相关的段落反而进不来。重排序在按相关度排序之后，先保证每份来源文档至少有一条入选， 再用剩下的名额按分数补齐。 The top hits often come from adjacent chunks of the same document — near-duplicates that crowd out the context window while genuinely relevant passages from other documents never make it in. The reranker sorts by relevance, then guarantees at least one chunk per source document before filling the remaining slots by score.

实现上没有引入交叉编码器模型——那会带来一个额外的模型下载和推理开销。 这里用的是检索阶段已有的分数做排序，对规模不大的知识库足够，也保持了零额外依赖。 No cross-encoder model is involved — that would add a model download and inference cost. Ranking uses the scores retrieval already produced, which is enough at this scale and keeps the dependency list short.

三、带引用的回答3. Answers carry citations

模型被要求只依据检索到的片段作答，并标注每句话来自哪个片段；界面上这些引用可以点开看原文。 这既是给用户的信任依据，也是调试检索质量最直接的手段——回答错了，看引用就知道是检索没捞到还是模型读错了。 The model is instructed to answer only from retrieved passages and to mark which passage supports each statement; in the UI those citations open the original text. That's trust for the reader, and it's also the fastest way to debug retrieval — when an answer is wrong, the citations tell you whether retrieval missed or the model misread.

关于这个项目Origin

这是我在学习检索增强生成时做的完整实现，重点不在「能问答」，而在于把检索这条链路上 每个环节都拆开想过一遍——为什么要混合检索、为什么要按排名融合、重排序解决的是什么问题。 这些判断是在动手之后才真正理解的，所以我把它们写在这里而不是藏在代码里。 I built this while learning retrieval-augmented generation. The point wasn't "it answers questions" but taking each stage of the retrieval path apart — why hybrid search, why fuse on rank, what reranking is actually for. Those are judgements I only understood by building it, which is why they're written down here instead of left in the code.
