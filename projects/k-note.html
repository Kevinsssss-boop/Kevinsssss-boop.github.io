K记 · 个人记账K-Note · Personal Ledger

一个自己每天在用的记账应用。两级分类、预算提醒、图表统计， 数据完全存在本机，不联网、不上云。 A bookkeeping app I actually use daily. Two-level categories, budget alerts, charts — with all data stored locally, no network, no cloud.

这是一个纯前端版本，数据存在你自己浏览器的 localStorage 里，关闭后不会上传到任何地方。 写进去的账目只有你自己看得到，可以随便试——右下角有「清空重来」。 This is the pure-frontend build: data lives in your own browser's localStorage and is never uploaded. Anything you enter stays with you — there's a "reset" button in the bottom corner.

为什么是两级分类Why two levels of category

大多数记账应用给的是一排扁平分类：餐饮、交通、购物……问题是「吃」这件事在生活里 其实是分开的——食堂的午饭和周末的朋友聚餐，花的是同一笔钱，但想控制的东西完全不同。 用一级分类看总量、二级分类看结构，才能真正回答「这个月为什么超了」。 Most expense trackers give you one flat row of categories. But "food" isn't one thing in practice — a canteen lunch and a weekend dinner out come from the same budget line while being completely different habits. A top level for totals and a second level for structure is what actually answers "why did I overspend this month".

所以内置了 11 个大类、55 个小类，每个小类配一个 emoji 图标。同时允许自己增删改分类—— 预置分类不可改，自建分类独立存放，不会互相污染。 So there are 11 top-level categories and 55 sub-categories, each with its own emoji. You can also add, edit and delete your own — presets stay immutable and custom categories are stored separately, so the two can't contaminate each other.

一个刻意的架构选择：同一份代码跑两种环境A deliberate choice: one codebase, two environments

存储层写成了一个环境自适应的模块：检测到 Electron 就通过 IPC 读写本地文件， 否则退回 localStorage。上层组件完全不知道自己在哪种环境里运行。 The storage layer adapts to its environment: under Electron it reads and writes a local file over IPC, otherwise it falls back to localStorage. Nothing above it knows which one it's running in.

这个决定的直接好处是：桌面版和网页版共用一套逻辑，测试也只需要针对界面行为写。 上面那个在线 demo 用的就是同一份构建产物，只把 Service Worker 注册去掉—— 对演示来说，离线能力没有价值，反而会引入「我更新了、访客却看到旧缓存」的问题。 源码里的 PWA 支持保留着，去掉的只是部署时的那一行注册。 The payoff is that the desktop and web builds share all their logic, and tests only need to cover UI behaviour. The demo above is the same build output with the service-worker registration removed — offline support is worthless in a demo and actively harmful when it means "I shipped an update but visitors see a stale cache". The PWA support stays in the source; only that one registration is dropped at deploy time.

我修的一个缺陷A bug I fixed

项目此前构建不通过。统计页有个多余的右花括号， 让整个构建在打包阶段直接失败——也就是说，从引入它的那次提交之后， 这个项目就再没成功构建过，而那次提交的说明恰好写着「代码质量全面提升、90 个单元测试全部通过」。 单元测试覆盖的是逻辑，不会去解析 JSX 语法，所以没能拦住它。 The project didn't build. A stray closing brace in the stats view failed the whole bundle step — meaning it hadn't built successfully since the commit that introduced it, a commit whose message read "code quality fully improved, all 90 unit tests passing". The tests cover logic and never parse JSX syntax, so nothing caught it.

关于演示数据About the demo data

上面那个 demo 里的账目是程序生成的虚构数据，由固定随机种子产生，不含任何真实消费记录。 之所以预置而不是留空，是因为空账本看不出这个软件能做什么； 之所以加一条说明，是因为不说明的话，访客可能会以为那是我的真实账单。 The entries in the demo above are synthetic, generated from a fixed random seed, and contain no real spending. They're pre-loaded because an empty ledger doesn't show what the app does — and they're labelled because without that label a visitor might reasonably assume it's my actual spending.
