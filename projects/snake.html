工程上值得说的四件事Four things worth explaining

1. 碰撞检测用空间哈希1. Collision detection uses a spatial hash

朴素的碰撞检测是「每条蛇的每一节 × 每个食物 × 每个道具」，11 条蛇平均 60 节、 150 个食物，每帧大约十万次检测，帧率直接崩掉。改成均匀网格分桶之后， 每次查询只碰自己附近的格子，单帧开销跟「附近有多少东西」相关，而不是跟世界里的总数相关。 The naive version is every segment of every snake against every food orb and power-up. With 11 snakes averaging 60 segments and 150 orbs that's roughly 100k checks per frame — the frame rate collapses. A uniform grid buckets entities by cell instead, so a query only touches its own neighbourhood and the per-frame cost tracks what's nearby, not what's in the world.

2. 把 4,100 行的单文件拆成 39 个模块2. Splitting a 4,100-line file into 39 modules

不是「模块化更好」，是这个文件确实撞到了天花板：编辑工具在匹配大段代码时开始出错， 而加一套新皮肤要在相隔几百行的三个地方插入代码，很容易漏掉一处。 Not because modular is nicer — because the file had hit a real ceiling. Editor tooling started mis-matching large blocks, and adding one skin meant editing three places hundreds of lines apart, where missing one was easy.

拆法是纯物理移动：不改任何逻辑、变量名或函数签名。模块按文件名数字前缀排序， 由一个 30 行的零依赖脚本拼接回单个 HTML 文件。全局状态（canvas、ctx、 camX 等）刻意保留为全局——这些名字在几百处被引用，把它们改成模块导出是一次重写，不是重构。 The split was purely physical: no logic, variable name or function signature changed. Modules are ordered by numeric filename prefix and concatenated back into one HTML file by a 30-line zero-dependency script. Global state (canvas, ctx, camX…) deliberately stayed global — those names appear in hundreds of places, and turning them into module exports would be a rewrite, not a refactor.

改完之后，加一套皮肤从「在 4,100 行里找三个插入点」变成「写一个 60 行的文件 + 改一行数组」。 拆分前后对比过标识符数量和语法检查结果，确保没有代码在移动中丢失。 Afterwards, adding a skin went from "find three insertion points in 4,100 lines" to "write one 60-line file and add one array entry". I diffed identifier counts and syntax-checked every module against the pre-split baseline to be sure nothing was lost in the move.

3. 渲染器用策略模式，不用 switch3. Renderers use a strategy table, not a switch

9 个渲染器各画各的身体和头。如果核心渲染循环里写一个按皮肤 id 分支的 switch， 那么每加一套皮肤都要动核心代码——正是拆分要消除的那种耦合。改成渲染器自己注册进分派表之后， 一套皮肤就是一个自包含的文件。 Nine renderers each draw their own body and head. A switch on skin id inside the core render loop would mean every new skin touches core code — exactly the coupling the split was meant to remove. Each renderer registers itself in a dispatch table instead, so a skin is a self-contained file.

4. 性能取舍：先保效果，再上 LOD4. Performance: keep the effects, add LOD

粒子爆炸和逐节辉光就是这套视觉的辨识度，为了帧率把它们砍掉是错的取舍。 做法是预分配 350 个粒子的对象池（每帧不分配内存，也就没有 GC 停顿）， 再对屏幕外和远处的实体降级——而不是全局删掉效果。 Particle explosions and per-segment glow are the visual identity here; cutting them for frame rate would be the wrong trade. Instead there's a pre-allocated pool of 350 particles (no per-frame allocation, so no GC pauses), and effects are downgraded for off-screen or distant entities rather than removed globally.

修过的一个缺陷A bug I fixed

双人模式里 P2 无法加速。教程卡片一直写着「WASD 移动 + Tab 加速」， 但代码里没有任何地方处理 Tab 键：getPlayer2() 定义了却从未被调用， 而 getPlayer() 明确排除了 P2，松开加速键时也只释放 P1。 结果就是 P2 能动、不能加速。补上 Tab 处理时必须同时 preventDefault—— Tab 的默认行为是把焦点移出画布，不拦截的话按一次之后整局都收不到键盘事件。 Player 2 couldn't boost. The tutorial card always said "move with WASD, boost with Tab", but nothing handled the Tab key: getPlayer2() was defined and never called, getPlayer() explicitly excludes P2, and the boost-release handler only cleared P1. So P2 could move but not boost. Adding the handler also required preventDefault — Tab's default is to move focus out of the canvas, and without catching it one keypress would kill all keyboard input for the rest of the game.
