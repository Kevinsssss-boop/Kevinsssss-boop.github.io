合同字段提取工具Contract Field Extractor

一批多语种劳动合同需要录入员工系统。人工做法是一份份打开 PDF，找到姓名、薪资、 银行账号、试用期等字段，逐条敲进表格。这个工具把「找到」自动化，把「确认」留给人。 A batch of multilingual employment contracts had to be entered into an HR system. Manually that means opening each PDF, hunting down name, salary, bank details, probation period, and typing them in. This tool automates the finding and leaves the verifying to a human.

设计上最关键的一个决定The key design decision

不让人去核对一张表格，而是让人核对 PDF 原文。 自动提取的字段一定会错，问题是怎么让错误被发现得足够快。如果只给出一张「字段 → 值」的结果表， 复核的人必须回头翻 PDF 才能判断对不对，而这正是最慢的一步。 Reviewers verify the PDF, not a table. Extracted fields will be wrong sometimes; the real question is how fast a wrong value gets noticed. If all you get is a field-to-value table, the reviewer has to go back to the PDF to check anything — which is exactly the slow part.

所以这个工具在右侧显示 PDF 原文，选中某个字段就在原文里高亮它的位置，两边联动。 复核从「翻文件」变成「看一眼」。同一个思路也用在校验上：字段值改完立刻重跑校验规则， 不符合预期格式的当场标黄并说明期望值。 So the app shows the source PDF alongside the fields and highlights the matched text, keeping the two in sync. Checking goes from "find the document" to "glance right". The same idea drives validation: editing a value re-runs the rules immediately and flags anything unexpected, with the expected format spelled out.

我做了什么My part

功能是完整的，问题出在「出错的时候」。我系统地把失败路径走了一遍，修掉的是这些—— The features were all there; the problems were in what happened when things went wrong. I went through the failure paths systematically and fixed these —

  • 密码错误被当成「处理成功」。解密失败的异常消息里含「解密」二字， 而判断能否自动重试的代码找的是「加密」——一字之差，这个错误就被当成可重试的临时故障吞掉了。 文件最终被标记为完成并写入一整批空字段，用户看到的是成功。 改成用异常类型判断，需要人工介入的错误一律原样上抛。 A wrong password was treated as success. The decryption error message contained "decrypt" while the retry logic looked for "encrypt" — one character apart. So the error was swallowed as a transient failure, the file was marked complete, and a full set of empty fields got written. The user saw success. Now these are distinguished by exception type, and anything needing a human is raised as-is.
  • 重提一次，人工修正值全丢。原流程是「读旧值 → 删掉旧记录 → 调模型」， 模型一失败就走异常分支，读出来的旧值当场丢弃；重试时表已经空了，读回来自然什么都没有。 改成模型调用全部成功后才替换旧记录。 Reprocessing wiped every manual correction. The order was "read old values → delete old rows → call the model". Any model failure jumped to the error branch and dropped the values it had just read; by the retry the table was already empty. Now the old rows are replaced only after every model call succeeds.
  • 配置页会把密钥存坏。界面把 API Key 显示成掩码，保存时又把掩码原样写回， 于是真正的密钥被一串圆点覆盖，且不可恢复。改成掩码值直接忽略不写，并把两个表单实例拆开 （原先两张卡片共用一个表单实例，互相污染）。 The settings page corrupted API keys. The UI showed a masked key and then wrote that mask straight back, overwriting the real secret with dots — unrecoverable. Masked values are now skipped on write, and the two cards no longer share one form instance (which was letting them contaminate each other).
  • 全部失败时进度条停在 0%。失败路径只发了错误事件，而计数器是在完成事件里推进的， 于是整整一批文件全失败，界面显示的一直是「刚开始」。现在失败同样发出完成事件并计入失败数。 A fully failed batch showed 0% progress. The failure path only emitted an error event, while the progress counter advanced on completion events — so a batch where everything failed looked like it had just started. Failures now emit a completion too, counted in the failed total.
  • 双击图标会丢数据。开两个实例时，各自持有一份内存数据库， 退出时全量覆盖同一个文件，后关的那个把前一个的校对成果整个抹掉。加了单实例锁。 Double-clicking the icon lost data. Two instances each held their own in-memory database and wrote the whole file back on exit — the last one to close erased the other's review work. Added a single-instance lock.
  • 服务挂起会拖死整批。模型和 OCR 请求没有超时，服务端不响应时并发槽位永久占用， 只能杀进程。补上超时。 A hung service stalled the batch. Model and OCR calls had no timeout, so an unresponsive server held the concurrency slots forever and the only way out was killing the process. Timeouts added.
  • 导出的两列永远是空的。导出时按固定列清单写入，但其中两列的取值逻辑 从未被接上，于是每次导出的这两列都是空值，且不报错。 Two export columns were always empty. The exporter wrote a fixed column list, but two of them never had their value lookup wired up — so they came out blank every time, silently.

数据流向Where the data goes

这个工具会把合同全文发给外部服务：文本送给大模型做字段抽取， 扫描件的整页图片送给 OCR 服务。所有数据保存在本机，但这两次外发是提取功能的前提。 内部工具部署时会先说明这一点。 This tool sends contract text to external services: the text goes to an LLM for field extraction, and scanned pages go as images to an OCR provider. Everything is stored locally, but those two calls are what makes extraction possible. Anyone deploying it internally should know that up front.

为什么源码不公开Why the source is private

字段体系、校验规则和提示词都是围绕真实业务口径设计的，属于内部信息。 这里展示的是工程判断，不含业务数据。 The field schema, validation rules and prompts are built around a real business framework and count as internal. What's here is the engineering judgement, with no business data.
